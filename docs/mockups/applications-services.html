Applications and services — mockups

Services today are one collapsible group under Configure, ten pages deep, each shaped like the schema block behind it. This splits them in two: Applications becomes a top-level menu for the things someone adds because of what they do, and the plumbing stays a sidebar group, moved under System and down to six. Palette, spacing and controls are taken from src/app.css, so these read as the real app.

1 — Applications › AdGuard Home, off

An application that is not switched on has nothing to configure, so the page is what it does and one switch. The sidebar is the catalogue: only applications this device reports as installed appear, because the app cannot install a package it lacks.

Only what the device has. The sidebar is service_entries() narrowed by the modules list the device returns at login — adguardhome, tailscale and qosify here. An application whose package is missing is not drawn at all, since the app has no way to install one. Against the mock AP that hides nothing; against a device without qosify, Quality of Service simply is not in the list.
Is the sidebar catalogue enough? Drawn as one page per application, matching how every other section works. With three entries the sidebar answers "what do I have?" on its own. The alternative is an Overview entry above them holding a card per application with its switch, which reads more like an app list but adds a page that says nothing the sidebar does not.

The odd one. It is switched on by neither a block nor a service list but by the uplink's speeds being known, so the page asks for those first and says why. The named traffic classes come from qosify's own qos.json, grouped into things people recognise rather than listed as service names.

Field mapping.
  • Line speed → interfaces.wan.quality-of-service.bandwidth-up and bandwidth-down, in Mbit. These are the switch: has_qos_interfaces() requires an upstream interface with both set, and disables qosify otherwise.
  • Give priority to → services.quality-of-service.services, an array of names from qos.json. Each toggle stands for a group of them.
  • Behind Advanced → bulk-detection.dscp, bulk-detection.packets-per-second, and the classifier array of port and DNS rules.
This one could belong on WAN instead. Two of its three controls are properties of the uplink, and the Network mockup already lists quality-of-service under "per interface, still to place". Drawn here because a user looking for "make video calls work" will not look under WAN, and because the classes and classifiers have nowhere sensible to sit there. The alternative is line speed on WAN and the rest behind an Advanced disclosure on that page, with no application at all.

4 — System › Services

What is left once the applications have gone: plumbing that makes the device manageable or discoverable rather than anything a network is for. Services expands in the sidebar rather than sitting behind a list page, which is the group pattern Configure already uses — reaching one is a click, not two, and the menu stays a menu rather than becoming a page that only holds links.

A service is given to a network from the service's own page. "Reachable from" writes ssh into each interface's services array — the same array Configure › Interfaces offers as a checkbox list. Asking here is the right way round: someone turning on SSH is thinking about SSH, not walking the interfaces to remember which of them should carry it. It also puts the switch and its scope in one place, which is what makes a single switch honest. Configure › Interfaces keeps its checkbox list: the raw editor edits the document as the schema shapes it, and two views of one array is the ordinary case there.
Renamed, not reinvented. mDNS, LLDP and 802.1X are drawn under what they do, with the protocol name kept in the hint so anyone searching for it still lands here. The keys are unchanged: services.mdns, services.lldp, services.ieee8021x. SSH and RADIUS keep their own names because those are the plain words for them.
RADIUS and wired authentication are one thought. 802.1X's only setting is which RADIUS server to ask, and the usual answer is the built-in one directly above it. They are drawn as two rows here; one row called Network access holding both would be fewer decisions, at the cost of hiding that either can be used without the other.

Where this lands in the bar. Applications sits after Network and before Configure: Status · uCoord · Wireless · Network · Applications · Configure · System, with Changes appended only while something is pending. Services becomes a group: true entry in SYSTEM_ITEMS beside Device and Time — which is what ChangesPanel.svelte has been labelling these all along (unit → "System › Device", ntp → "System › Time", service:* → "System › Services"), so the changes list needs no relabelling.
Two groups where the nav supports one. group: true exists once today, and SectionNav.svelte holds a single servicesOpen state for it, opened by an inServices predicate hardcoded as page.startsWith('service:') || page === 'ntp' in both SectionNav.svelte and App.svelte. A second group needs that generalised to per-group state, and the duplicated predicate reduced to one. Applications is a section rather than a group, so it does not add a third.

7 — What "on" actually means

The load-bearing part. A single switch per application looks obvious in a drawing, but the device starts these five different ways, and today's toggle writes only one of them.

Started by a network listing it
sshinterfaces.*.services
mdnsinterfaces.*.services
lldpinterfaces.*.services
adguardhomeinterfaces.*.services
tailscaleinterfaces.*.services
The template calls lookup_interfaces() and returns early when nothing lists it, so the settings block alone starts nothing.
Started some other way
logthe block existing
radius-serverbeing installed at all
ieee8021xieee8021x-ports set
quality-of-servicebandwidth-up and -down set
ntpdefinitions.ntp-servers non-empty
Four mechanisms across five services. None of them is the enable toggle the UI currently draws.
Today's toggle is half a switch. service_enable() and service_disable() in src/lib/store.svelte.ts add and remove the services.<key> block and nothing else — the comment on service_disable says interface service lists are deliberately left alone. For the five in the left column that means switching one on in the UI starts nothing on the device, and switching it off leaves it running. Any single-switch page has to write both places, which is why "Filter for" and "Reachable from" are drawn as first-class controls rather than buried.
And what "off" should mean. Removing the network from the list stops the service but keeps its settings; removing the block loses them. Both are defensible and they are not the same, so this needs deciding before any of it is built. The guest network settled the equivalent question by keeping the whole object and setting disable — services have no such flag.

Two of the six are user-facing. samba4 is file sharing and fingerprint is why the client list shows "Living room TV" rather than a MAC address — both are things someone would look for. Neither has a settings block, so each would be a switch and nothing else, and per the uconfig repo samba4 is not wired into the template set at all yet. The remaining four are internal and should probably never appear: webui is what is serving this page.
Configure's fate is only half answered here. Moving services out leaves interfaces, radios and JSON, which are the raw editor and not intent pages at all. Whether the live app keeps a raw editor beside the intent pages, or drops it and sends anyone who needs it to the offline build, is the decision underneath open question 1 in live-app-navigation.md — and this artefact does not settle it.
