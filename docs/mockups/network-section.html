Network section — mockups

A new top-level Network menu with five sidebar pages: Wireless, Guest, Radios, WAN and LAN. Every page is intent-shaped — it asks what you want the network to do and works out the schema fields itself, rather than presenting the document's own structure. Palette, spacing and controls are taken from src/app.css, so these read as the real app.

2 — Network › Guest

Guest is a whole interface, not just an SSID: its own VLAN, its own subnet, and barred from the networks upstream of it. The page presents that as one switch with consequences, rather than four separate objects.

Two ways out, and this needs your call: (a) Wireless owns the main network only and Guest owns its own — the split shown here; or (b) Wireless lists every SSID and Guest holds only the switch, VLAN and subnet.

Field mapping.
  • Channel → radios.2G.channel (auto or a number), width → channel-width
  • Transmit power → tx-power in dBm, presented as four named steps rather than a number. Maximum writes 30, which is also the schema default, so choosing it clears the field.
  • Behind Advanced: channel-mode, require-mode, he-multiple-bssid, legacy-rates, allow-dfs, maximum-clients, rates. Present but collapsed, so the default view stays plain without putting anything out of reach.
Advanced is the open question here. The band-level fields above have no plain-language equivalent, so they either sit behind a disclosure on this page or become unreachable. I have drawn the disclosure; the alternative is a deliberate decision that this UI does not set them at all.

Two decisions before building.
  • Changes and Apply. These pages edit one document, so a single pending set and one apply is the honest model. A Changes entry inside Network is fine; two independent apply buttons over the same document would not be.
  • AP mode. In AP mode there is no LAN interface and WAN carries every port, so LAN and much of WAN do not apply. Either hide the pages, or show them explaining that the upstream router owns those settings.

What this needs. The entries already carry everything required — ChangeEntry has a scope (the page that owns it) and a doc (main config or a named include), so grouping by origin is a regrouping of data that exists, not new tracking.
  • SECTIONS gains a changes entry with no sidebar items, filtered out by sections_for() when the count is zero — the same whenChanges rule that governs the current sidebar item, lifted to the top level.
  • Grouping moves from ChangeEntry.section (‘Unit’, ‘Radios’, …) to the owning page, so the labels match the menu the user actually clicked.
  • Per-group Reset reuses scope_reset(scope) unchanged.
One thing to decide. The section disappears the moment the last change is reset or applied — so the page you are looking at vanishes under you. Either fall back to the previous section on the transition, or keep the entry visible while it is the active section and drop it on the next navigation.
