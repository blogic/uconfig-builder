Status — mockups

Status can only show traffic and a client list, because until now nothing told the app what the device was doing. Three RPCs change that, and three pages read them: Internet for the uplink, Network for the wired side, Wireless for the radios. Every number below is real, read off a GL-MT6000 and then scrubbed of its addresses. Palette, spacing and controls are taken from src/app.css, so these read as the real app.

1 — Status › Internet

The page for "is the internet alright". Traffic moves here from its own entry: throughput is a property of the uplink, and someone watching the graph wants the address and the lease in the same glance. Reads network, ports and the existing traffic.

Field mapping. Three calls, one page:
  • Connected, uptime → network.wan.up and uptime. The heading is the answer to the question the page was opened with, so it is the first thing rendered.
  • Uplink card → network.wan.ipv4: address, gateway, dns, lease.server. Renews in is lease.time counted against uptime, because "864000 seconds" is not an answer.
  • IPv6 card → network.wan.ipv6. Delegated to us is prefix, the /62 the ISP handed down; handed on is the /64 this device assigned to the LAN, from network.main.ipv6.assigned.
  • Socket → ports.WAN: carrier, speed, netdev and the byte counters. Throughput stays on the existing traffic feed.

Field mapping. This device → network.main: ipv4.address and ipv6.assigned, which carries both the global /64 delegated from the uplink and the ULA the device always has. Sockets → ports minus the WAN entry, in index order; no cable is carrier: false, where speed is null. Client counts are the existing devices reply, split on whether an entry has a wifi block.
The names do not match. ports calls them WAN and LAN1…, while capabilities and the Ports config page call the same sockets eth1 and lan1…. Drawn with the friendly names, since these are the labels printed on the case, but a device configured by port name shows the other set two menus away. Either the state reply carries both, or the config pages adopt these.

Field mapping, and why two channel numbers. radios.2g carries both channel, what the config asked for, and active_channel, what the radio picked. "0" means automatic, so the page reads 11 · chosen automatically; 5 GHz has channel: "36" and lands on 36, so it reads set in the config. Showing only one of the two loses the answer to "I set automatic, what did it do".
  • Width → bandwidth, mode → mode rendered as its marketing name.
  • Airtime → utilization, a percentage from hostapd. The ramp matches UsageGauge.svelte: accent under 75, amber to 90, red above.
  • bandwidths and channels are also in the reply — what this radio could still be moved to. Not drawn: that is a change, and this section only reports.
Client counts are not in the reply. radios says nothing about who is associated. The numbers above are countable client-side by grouping devices on wifi.band, which is what the drawing assumes — but that payload spells the band 5G while radios keys on 5g, so the join has to fold case. The alternative is a station count in the RPC, which the device already knows.

5 — Where they sit

Status holds two pages today, one of which is a graph with no context. Three named pages replace it, and Traffic stops being a page of its own.

⚙ uConfig
Status Wireless Network System
📈 Traffic
👥 Clients

Today. A throughput graph and a list of clients. Nothing says whether the uplink has an address, which channel a radio chose, or whether a cable is in.

⚙ uConfig
Status Wireless Network System
🌍 Internet
🖧 Network
📶 Wireless
👥 Clients

Proposed. Four pages, each answering a question someone arrived with. Traffic folds into Internet, where the throughput has an address beside it.

Two knock-on effects. STATUS_ITEMS[0] is where a session lands after login, so Internet becomes the landing page — which is the right one. And the mobile bottom bar spreads every Status item, so it goes from two icons to four; that is its whole budget, and a fifth Status page would need a different answer on phones.

6 — What the calls return

Three methods, all authenticated, none addressed. radios and ports already exist on the device as ubus call state …; network is new and specified in device-state.md. All three are mocked, so the pages can be built before the device side lands.

Why network needs writing rather than proxying. netifd splits one uplink into three interfaces — wan carrying the link, wan_4 the DHCP lease, wan_6 the prefix — and none is named after the document. uconfig already stamps each generated section with option uconfig_name 'wan', so the new method groups network.interface dump by that tag and folds the families into one entry. Without it every page would have to know that wan_6 belongs to wan, which is netifd's business and changes with the proto.
The bridge is broken today. handle_radios and handle_traffic in the AP's uwsd-handler.uc call ubus.call('uconfig-ui', …), and no such object exists — the publisher is state. On the device, ubus call uconfig-ui radios answers Command failed: Not found, so both RPCs fail on real hardware while working against the mock. ports has no bridge at all. Three lines in the AP repo, but nothing here works on hardware until they land.

An access point has no Internet page. In AP mode there is no wan in the document and the device holds no uplink, so the page has nothing to report — the same shape as Network › Guest, which is absent rather than apologetic when the device does not route. Network and Wireless still apply and are the pages that matter there.
