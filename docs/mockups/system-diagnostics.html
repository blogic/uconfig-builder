System diagnostics — mockups

Two questions the app still cannot answer: what just happened, and why is the memory climbing. The device already knows both — ubus call event log keeps the last hundred things it did, and ubus call memory info watches every process — and neither is bridged to the web UI. Two pages read them, both under System. Every number below is real, read off a GL-MT6000 and then scrubbed of its addresses. Palette, spacing and controls are taken from src/app.css, so these read as the real app.

One sentence per event, not a field dump. Every entry is {object, verb, time, ...payload} flattened together, and the page owes each combination a sentence:
  • client/join → handset joined uconfig-demo on 2.4 GHz, channel 11
  • client/leave → console left after 1h 49m, 167.8 MB down, from connected_time and rx_bytes
  • dhcp/ack → Handed 192.168.42.17 to workshop-pc
  • carrier/up, carrier/down → Cable plugged into LAN2. name is a socket label, matching ports rather than capabilities
  • ssh/event → the message verbatim; it is already a sentence
The name comes from devices, keyed on the MAC. A device that has never appeared there keeps its MAC, which is the honest answer rather than a gap.
Sort by time, always. The daemon writes events[event_count % 100] and the log method returns slot order, so a buffer that has wrapped begins in the middle with the oldest entry. The fixture is stored rotated for exactly this reason: a client that forgets to sort should look wrong against the mock rather than only against a device that has been up for a day.

Four filters, not a search box. All, Clients (client and dhcp), Wi-Fi (wifi), Device (carrier, ssh, and anything unrecognised). A hundred entries do not need searching, and .tabs-inline is already the app's control for exactly this — the traffic range picker on Status › Internet is the same thing. The app has no search input anywhere and this is not the place to introduce one.
The vocabulary is open, so nothing may be dropped. The event ubus method takes any object and verb from any caller, and the dhcp verb is whatever dnsmasq's notify says after the dot — ack is only the one that turns up most. wifi/channel-switch forwards hostapd's payload unchanged and has no fixed shape at all. A page that renders only the combinations it knows will silently swallow the rest, so the fallback prints object verb and the remaining fields, and the Device filter is where it lands.

An empty log is a fact about the device, not about the network. "No events" would read as "nothing has happened", and someone would conclude their clients are not connecting. It has to say why it is empty, which is the same reason it will be empty again after the next firmware upgrade.

The device says "leaking" and the page must not repeat it. The entire rule in umemd is if (delta_rss > 0 || delta_fds > 0) — any growth at all, by any amount. On this reading that flags 18 of 44 processes, and the last of them has grown by 8 kB. Printing the word would tell someone eleven daemons are leaking when none of them is. So the headings are Grown since first seen and Steady, the figure is shown, and the number carries the argument. The split is still worth keeping: it is the device's sort key, and everything above the fold really is what grew.
Two halves, two ages. system is read from /proc/meminfo when the call arrives, so the gauge is live. The process lists come from a table resampled every hour, so polling this at 10s like the Status feeds would draw a frozen table beside a moving gauge. Poll at 60s and say sampled hourly on the page, as the Processes card does.
"First seen" is umemd's first sighting, not the process's start. New pids are picked up by a 60 second scan, so anything already running when umemd started is baselined at its first sweep — rss_startup_kb for a boot-time daemon means "RSS shortly after boot", and age_s is how long it has been watched, not how long it has run. After a umemd respawn every baseline resets and the whole list reads steady for an hour. Hence the wording: grown since first seen, which is exactly the claim the data supports. Note also that Steady holds processes that shrank — tailscaled is 12 MB smaller than when it was first seen.
This page never reads system-info. Overview's memory gauge comes from there, and the two calls report the same quantity in different units — kB against bytes — sampled at different instants. A page mixing them would show two totals that disagree by a few hundred kB and look broken.

6 — What the calls return

Both top level, both authenticated, neither addressed. Each passes the ubus reply through unchanged, the same as radios, ports and network.

Neither is bridged, and they come from three different daemons. Nothing in the AP's uwsd-handler.uc calls event or memory; each needs a handle_<name> following handle_traffic and one line in the handlers table. state ships in uconfig-mod-state, event in base uconfig, and memory in umemd, which is not in the uconfig tree at all — so the bridge has to report a missing feature rather than an internal error when the object is absent, and the Memory page needs a state for a device that cannot answer.

7 — Still to place

Decisions these drawings do not make.

  • No sampled_at. The payload never says when the process figures were taken, so the page can say "hourly" but not "11 minutes ago". The device adding one timestamp would fix it.
  • age_s is observation time. There is no process start time in the payload, so the page cannot say how long something has actually been running — only how long it has been watched.
  • Growth needs a rate, not a total. +30 MB over 32 hours and +30 MB over 20 minutes are very different, and only the second is worth waking up for. Both rss_delta_kb and age_s are there, so the page could divide; whether a rate reads better than a total to someone who is not a developer is untested.
  • Whether the log should be live. The event object supports ubus subscription and pushes each entry as it happens. Polling is enough at a hundred entries, but a page someone leaves open while walking a client round the house wants the push.
  • wifi/channel-switch has no fixed shape — it forwards hostapd's payload. The sentence here reads freq, channel and bandwidth, which is what hostapd sends today and not a contract.
  • Day boundaries. The drawing shows one day. A hundred entries can span several, and the log carries no timezone: the timestamps are the device's clock, so the page should read sysinfo.localtime as "now" rather than the browser's, or a device with no working NTP will report its own events in the future.
  • Nothing links out. A client name in the log is the same client as on Status › Clients, and a socket label is the same socket as on Status › Network. Neither is a link yet.
